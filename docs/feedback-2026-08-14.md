## Bug 1: 会话统计条不显示 "LLM 时长 · 工具调用时长"

**标题**: Web UI 统计条缺少 LLM/工具调用耗时组

<details>
<summary>复现、预期与验收</summary>

- **复现步骤**:
  1. `dsh web` 启动
  2. 新会话完成多轮对话(含多次工具调用, 如 Read/Grep/Glob)
  3. 查看输入框上方统计条
- **实际结果**: 统计条只显示 "N 轮 · M 步 | 首 token 平均 X · Y tok/s | 缓存命中 Z% | 输入 A tok · 输出 B tok", **缺少 "LLM XmXs · 工具调用 YmYs" 段**
- **预期结果**: 显示 "LLM 6m4s · 工具调用 1m26s" 组
- **根因(已排查)**: `StatsLine.tsx` 的 `deriveStats()` 依赖 assistant 节点的 `timing.stepStartTime/completedTime` 与 tool-result 的 `callTime` 计算 llmMs/toolMs。解压检查 session.jsonl.zstd: `step/start` 仅含 `{turn, step}`, `tool/result` 仅含 `time`, **无 timing/callTime 字段** → llmMs=0, toolMs=0 → 按 "a group with no data drops out whole" 整组消失
- **建议**: ①日志写入 timing 字段; 或 ②deriveStats 用事件 `time` 差值兜底(step/start 与 step/end 的 time 差 = LLM 耗时; tool/call 与 tool/result 的 time 差 = 工具耗时)
- **验收**: 真实会话下统计条完整显示 6 组

</details>

## Bug 2: 工作区设为盘根(F:\) 时 title 为空导致工作区失效

**标题**: 工作区路径为盘根时 title 为空, 会话无法附加

<details>
<summary>复现、预期与验收</summary>

- **复现步骤**:
  1. Web UI → 添加工作区 → 选择 `F:\`(盘根)
  2. 输入框仍只读, 显示 "选择一个工作区开始"
- **实际结果**: workspace.json 中 `title: ""`(basename("F:\\") 为空), 会话无法 attach, UI 不认该工作区
- **预期结果**: 盘根路径应有默认 title(如 "F:")或明确报错提示, 而非静默失效
- **根因**: `workspace.create({path})` 用 basename 派生 title, 盘根 basename 为空串
- **建议**: basename 为空时回退用盘符名(如 "F")或拒绝创建并提示
- **验收**: 选盘根时得到有效 title 或明确错误提示

</details>

## 建议 1: busyEnter=steer 语义弱于 codex 打断(插话仍是"下一步排队")

**标题**: steer 模式建议支持真正的"打断当前步骤"

<details>
<summary>详情</summary>

- **现状**: `busyEnter: steer` 时, agent 忙中回车 = `send(input, 'next-step', true)`(agent.ts:126), 消息插入 next-step 位但**不中断当前 step**; 当前 LLM/工具调用完成才轮到。源码注释也承认 "Direct steer is intentionally best-effort: AgentLoop turns a closed-window submission into the next waking Queue item"
- **体验**: 长工具调用(如 LSP/搜索)时, 用户插话要等当前 step 完成(可能 30s+), 与 codex 的即时打断体验有差距
- **建议**: 可选增强——steer 时若当前 step 超阈值(如 >5s 且非关键写操作), 触发 abort+重入(类似 cancel 但保留 inbox 语义), 让新指令立即接管
- **验收**: 长 step 中插话能在秒级响应

</details>

## 真心夸夸官方(实测感受)

用了几天, 说几个印象特别深的:

1. **架构是真的优雅**: "一切皆插件"(Cordis)不是口号——会话日志 append-only 单一事实源、能力缝三角色(Service Definition/Provider/Consumer)、waterfall 监听器, 这种把 agent 运行时拆到"每样东西都是可替换插件"的彻底程度, 业界少见。改一个工具就是挂一个插件, 不碰 loop。

2. **工程质量顶级**: 单文件 100% 覆盖率门控 + keyless 快照测试 + 契约验证, 这在 AI agent 项目里是奢侈配置。事件类型 30+ 每种都有明确 schema, 调试会话日志像读文档。

3. **会话日志设计是真聪明**: append-only + 投影派生, 重放/断点续跑天然成立。我们解压日志做故障分析, 每个事件都带 time 戳, 排查效率极高——这也是我们能快速定位 StatsLine 问题的原因。

4. **多agent委派是隐藏惊喜**: subagent/subagent_fork/send_message 工具链 + continuable 后台模式, 直接支撑了我们在壳子里跑 Miao 多agent协作框架(M1并行/M2分工/M5对抗), 几乎零适配。

5. **web UI 模块化(38个client包)**: ui-conversation/ui-trajectory/ui-settings 每个都是独立插件包, 我们注入皮肤(token 覆盖)/多语言/自定义标题栏时, 几乎不碰官方代码, 全靠 --dsw-* 语义 token 体系——这个设计给了第三方极大的改造空间。

一句话: **这是目前开源 agent harness 里架构和工程质量最接近"正经产品"的一个, rc 版就能有这完成度, 期待正式版。** 官方加油, 希望反馈的 2 个 bug + 1 个建议能帮到你们。
